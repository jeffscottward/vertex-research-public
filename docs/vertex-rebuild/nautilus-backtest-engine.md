## Run it

```sh
# One run: JSON request in, JSON result out (exit 2 on an input error).
cd services/research && python -m nautilus_backtest run request.json
# request.json: {"bars": {"t": [...], "o": [...], "h": [...], "l": [...], "c": [...], "v": [...]}, "spec": {...}}

# Parity suite (needs the Core 7 data from research/backtests/core7/fetch_data.py and a venv with the Nautilus lock).
bun run research:nautilus-parity -- --data ~/Documents/reports/vertex-core7/data \
  --python <venv>/bin/python --out research/backtests/nautilus-parity

# Golden fixture (TypeScript is the reference for the Python port).
bun run research:nautilus-golden  # scripts/research-nautilus-golden.ts

# Academy modelled options backtest on Nautilus option instruments (exit 2 on an input error).
cd services/research && python -m nautilus_backtest academy request.json
# request.json: {"bars": {"t": [...], "c": [...], "iv": [...]?}, "structure": "iron_condor", "rules": {...}, "capital": 100000}
bun run research:academy-golden   # scripts/research-academy-golden.ts
```

The `spec` has the fields of a backtest run spec: `rule` (`smaCross`, `breakout`, `rsiReversion` or `{"kind": "dsl", "definition": ...}`), `stopLossPct`, `takeProfitPct`, `costBps`, `costs` (`{"profile": <CostProfile>, "capital": n}` or null), optional `sectorQuadrants` and `initialCapital`. The result has the shape of the TypeScript `InstantRunResult`: `equity` (unit equity per bar), `trades` and `stats`. So `buildBacktestRunReport` and the analytics (deflated Sharpe, Monte Carlo, walk-forward, gs-quant analytics) read Nautilus results without a change.

## Backtest runs on Nautilus

Backtest runs (Backtest lab, Strategy builder, Autopilot "Run full backtest", library re-runs) run on Nautilus when the web app has `VERTEX_BACKTEST_RUNS_ENGINE=nautilus`. Unset or `typescript` keeps the API engine; nothing else changes. A stored run keeps its own engine id, so switching the setting never moves a stored run to the other engine.

1. `backtestRuns.submit` stores the run with the engine id `nautilus-trader-1.227.0` and does not run it in the API server.
2. The worker (`scripts/backtest-worker/nautilus-worker.ts`, `bun run vertex:backtest-worker:nautilus`) runs on the research host as a user systemd service ([infra/research-worker/README.md](../../infra/research-worker/README.md)). It calls `backtestRuns.engine.claim` over HTTPS with an operator agent write key. Claim moves the oldest queued run of the engine to `running` with a conditional update, so two workers never run the same run. It returns the spec, the bars of the date range (the same slice the API engine uses; JSON `null` for a missing value), the resolved cost settings, the sector rotation points that the definition's filters need and `series`: the daily series store rows (`id -> {dates, open, high, low, close, adjClose}`, up to `to`) that the definition reads, or null. `seriesSha256` is the bar series hash; for a run that reads series it also covers the rows, and for an options run it is the rows hash (an options run's bars are the run symbol's store row, not `market_bars`). A run whose inputs cannot be loaded fails at claim with the API engine's message.
3. The worker claims with `max` 50, so it gets a batch (one run, or up to 50 runs of one comparison group on one bar series), runs it in `VERTEX_WORKER_PROCESSES` processes of `python -m nautilus_backtest batch - -` in `services/research` (the shared bars and one case per run, with its index range, on stdin), and posts every result (`equity`, `trades`, `stats`, `engineRun`) and every input error (the same message as the TypeScript engine) with `backtestRuns.engine.completeMany`, in as few requests as stay under 900 KB each (the web app refuses requests over 1 MiB; 50 ten-year daily results are about 2.4 MB). A single result over that limit goes alone; when the API refuses it (413), only that run fails with "The Nautilus result is larger than the API request limit". Every request counts in the request budget. After a network error or a 5xx answer it tries again (4 tries, waits of 1, 2 and 4 seconds; a 429 is tried again once, after at most 125 s) and then fails the runs with "Could not deliver the Nautilus result"; any other 4xx fails them with "The API rejected the Nautilus result". Exit 3 (no Nautilus), any other exit, a different engine version, a process over 9 minutes or a worker stop: every run of that process fails with a short message, and the worker logs the engine stderr locally.
4. `complete` checks the result with the contract: finite numbers, unit equity above 0 at every bar, trade prices and units above 0, `stats.bars` equal to the equity length, trade bar indexes inside the series. It reloads the bars and refuses a result whose bar count or `seriesSha256` differs from the stored bars. It recomputes the stats from the stored bars and the worker's equity and trades with the TypeScript `summarize` and refuses a result whose stats differ by more than 1e-9 (relative); the refused run fails with the reason. It stores the API's own stats and builds the report with `buildBacktestRunReport`, the same code as the API engine. An options run (a dsl rule with an `options` block) is claimed alone (one in a comparison batch fails) and runs in the options runner (`strategies.qc_ports.portfolio.run_spec_json`, ledger plus NautilusTrader parity). Its result is that document (`kind: "options"`: capital, dates, equity, open positions, trades with each spread's `maxLoss`, size skips, book skips, signals, metrics, `nautilusGap`), validated strictly and bounded (20,000 days and 20,000 trades, unique trade ids, entries and exits on run days, `nautilusGap` required and at most 1e-6, the Python `PARITY_REL_TOL`). `complete` reloads the rows, checks the hash and runs the TypeScript options runner on them with the run's `from`, `to`, capital and symbol. The worker's ledger must be that run: the same run days, open positions, trades (ids, symbols, structures, expiries, strikes, dates, contracts and exit reasons equal; prices, return on risk and `maxLoss` within 1e-9; fees and P&L within one cent), skips and signals, the daily equity and the metrics within 1e-9 (relative). Any difference fails the run with the field that differs; a run the API cannot book fails with the runner's message. The report is the API's run (`buildOptionsRunReport`, the same as the TypeScript engine) with the worker's `nautilusGap`. `complete` and `fail` change only a run that is `running` on the same engine; anything else returns `CONFLICT` and changes nothing.
5. `backtestRuns.get` fails a Nautilus run that waited more than 10 minutes while no Nautilus run was claimed in those 10 minutes, so no worker is active ("Nautilus backtest worker did not pick up the run"). A busy worker never fails its backlog. A run left `running` for more than 10 minutes fails as for API runs. The Backtest runs and Strategy builder pages follow a run for up to 20 minutes.

Request budget: the worker backs off from 3 s to 45 s between empty claims, sends at most 150 requests before a 125 s quiet pause, waits 125 s after a 429 on a claim, and waits at most once (never past the API stale limit) after a 429 on a delivery. The agent key limiter resets a key's count only after more than 60 s without an accepted request, so a client that polls more often never resets it. With one Autopilot tick inside the pause, the two gaps add up to 125 s, so one is over 60 s; with two ticks, the gap between them is over 60 s. It depends on ticks being more than 60 s apart with one request each; a separate worker key is the robust fix ([infra/research-worker/README.md](../../infra/research-worker/README.md#request-budget)).

These are the defaults for a shared key. With its own write key the worker polls fast: `VERTEX_WORKER_IDLE_MS=3000`, `VERTEX_WORKER_IDLE_MAX_MS=3000`, `VERTEX_WORKER_REQUEST_BUDGET=550` (1 to 580) and `VERTEX_WORKER_QUIET_PAUSE_MS=65000` (at least 61000) give about 1.5 s average queue wait and one 65 s pause about every 27 minutes ([own key](../../infra/research-worker/README.md#own-key-fast-polling)). Web restarts: `infra/quantvps/restart-when-idle.sh` writes the worker pause file (`VERTEX_WORKER_PAUSE_FILE`) for its idle wait and removes it on exit; while the file exists and is younger than 90 min the worker claims nothing. It also claims nothing while another process holds the script's restart lock (`VERTEX_WORKER_RESTART_LOCK`), which covers older copies of the script that never write the pause file; it checks `/proc/locks` and runs `flock -n` only when the lock file's inode is locked ([web restarts](../../infra/research-worker/README.md#web-restarts)).

Monitoring: after 3 failed worker cycles in a row (API errors on claim or fail, a result that could not be delivered or was rejected, an engine crash, timeout or version mismatch; not a run's input error or an empty claim) the worker posts one alert line to the optional `VERTEX_ALERT_POST_URL` / `VERTEX_ALERT_CHANNEL` chat route, and one recovery line on the next normal cycle ([infra/research-worker/README.md](../../infra/research-worker/README.md#settings)).

The engine procedures need an operator agent write key; read keys and agent viewers cannot call them. A unit test (`packages/api/src/backtest-runs.test.ts`) feeds the TypeScript engine's result through `complete` and checks that the report equals the API engine's report. `scripts/backtest-worker/nautilus-worker.e2e.test.ts` runs the worker with the real engine against an in-process fake API when `VERTEX_NAUTILUS_PYTHON` is set:

```sh
VERTEX_NAUTILUS_PYTHON=<venv>/bin/python pnpm exec vitest run --config vitest.config.ts --project operations scripts/backtest-worker
```

## Dual run (engine comparison)

Owner decision (2026-11-05): Nautilus runs only on the rig worker, never on QuantVPS. The instant backtest, the parameter sweep and the Autopilot gate run both engines on the same request; owner decision 2026-11-08 adds setup replay and the paper forward tick (switch plan step 5), and the step 6 decision of the same day adds the Academy modelled options backtest: the TypeScript result is shown at once on the unchanged path, and the same run(s) are queued on Nautilus. Nothing switches. The setting is `VERTEX_ENGINE_COMPARISON` (`off` by default, `on`); `VERTEX_HOST_LABEL` names where the web server runs (default `web server`).

Storage: no new table. Each repeated run is a backtest run with the Nautilus engine id and `spec.comparison`: `feature` (`instant`, `sweep`, `autopilotGate`, `setupReplay`, `paperForward`, `academy`), `groupId` (instant, sweep, setup replay and Academy: `<feature>-` plus 32 hex of the SHA-256 of the canonical request content: series SHA-256, date range, rule or grid, stop, target and cost settings; the gate: `autopilot:<campaign id>`; paper forward: `paperForward:<monitor id>:<newest bar date>`), `label`, `key` (sweep cell index, Autopilot candidate id or drift monitor id), `dropped` (runs the cap left out) and `typescript`: its stats (the `InstantStats` fields), the trades as `[entry bar, exit bar, exit reason]` (at most 5,000), the trade count, `wallMs` and `host`. `backtestRuns.list` leaves comparison runs out; `backtestRuns.comparisons.list({feature?, groupId?, limit})` lists them (read keys may call it) with the status, the queue wait (`startedAt - createdAt`), `engineRun` and `differences`.

No flooding: the instant backtest and the sweep page run again on every form change. An identical request (same group id) whose group has a queued, running or succeeded run from the last 24 hours queues nothing new (a group whose runs all failed, superseded or for another reason, gets new runs) and shows that group (`reused: true`). A new group of the same feature from the same user fails that user's still-queued runs of older groups of the feature with "Superseded by a newer request" (one conditional update; running runs are never touched; the answer reports `superseded`). Both happen in one transaction under two advisory locks, taken in this order: feature and user (so two requests of one user run one after the other and the later one supersedes the earlier one, even when they arrive at once), then the group id (so two identical requests at once store the group once). A superseded request that is asked for again gets new runs in its group; the pages show the newest run per cell and "superseded" for the replaced ones. The gate's campaign group takes every tick's runs (no reuse, no superseding).

Only a caller that may write queues comparison runs: an operator session or a write-access agent key. `backtestRuns.sweep` is a read procedure, so a read-access key or a read-only agent viewer gets the TypeScript result without `comparison` and nothing is queued.

| Feature | What is repeated | Cap |
| --- | --- | --- |
| Instant backtest | The run over the whole stored series (`from` and `to` are the first and last bar dates) | One run per request |
| Parameter sweep | One run per evaluated cell (cells the TypeScript engine refused are not repeated), labelled with the cell's parameters | First 100 cells per sweep; the UI states it |
| Autopilot gate | For each candidate a tick gated: the in-sample slice and the full run whose tail is the out-of-sample part, as date ranges | 20 runs per tick; the runs record how many the cap left out |
| Setup replay | The setup's engine run over the whole daily series: its DSL definition (ATR stop and target), no costs and the time exit (`spec.maxHoldBars`, read by the Nautilus engine for DSL rules). The replay answer (occurrences, summary, Monte Carlo) stays the TypeScript one; the page shows the Nautilus card | One run per request; reuse and supersede as the instant backtest |
| Paper forward | The baseline run's spec from its start to the newest stored bar, once per monitor and newest bar: only a tick that recorded new bars and caught up queues it (a tick that recorded part of a long gap leaves it to the next). No `latest`, so the other monitors of one batch tick are never superseded. The paper points and trades stay the TypeScript ones | One run per monitor per new bar |
| Academy backtest | The lesson's structure with its resolved rules, the capital and the implied volatility per bar (the VIX closes for SPY when stored, else none: both engines then model it) on the daily closes the TypeScript run read, as a run with rule `{"kind": "academy", ...}` (see [Academy on Nautilus](#academy-on-nautilus-option-instruments)). The lesson page keeps the TypeScript result and shows the Nautilus card | One run per request; reuse and supersede as the instant backtest |

For the gate the TypeScript side is computed again on exactly the bars of each date range (for daily bars these are the gate's own bars; for minute bars the in-sample range ends with a whole day), and counts in the tick's time.

Timing: the server measures the TypeScript engine call. A Worker runtime does not advance `performance.now`/`Date.now` during pure compute, so a zero time is stored as `wallMs: null` with `wallNote: "timer frozen in Worker runtime"`, never as 0. The page also shows the browser round trip as the time the user saw. The worker records per run `engineRun`: `host` (`os.hostname()`), `wallMs` (engine time of the case), `processWallMs` and `cpuMs` (user + system CPU time of the engine process, from `getrusage`), `processes`, `processCases` and `gpu: "not used (Nautilus engine is CPU-only)"`.

Batches: `backtestRuns.engine.claim` takes `max` (1 to 50) and then returns a batch: the oldest queued run and, when it belongs to a comparison group, more runs of that group (a run without a group comes alone), with the bars from the earliest `from` to the latest `to` and each run's index range. `series` then holds every series that a run of the batch reads, each up to the latest `to` of the runs that read it, and a run that reads series has its own `seriesSha256` (its bars and its own rows). The claim loads the store once for a batch (every id its runs read, up to the latest `to`) and cuts each run's rows at its own `to`, which is what `complete` reloads; the Python batch cuts the rows of each equity case at its `to`. Rows over 40 MB of JSON (`BACKTEST_RUN_ENGINE_SERIES_MAX_BYTES`) fail the run at claim; a batch whose combined rows are over it fails its runs that read series. The worker splits the batch over `VERTEX_WORKER_PROCESSES` engine processes (default 8, at most 16; measured on the rig: 184 cells on 6,587 daily bars took 73.9 s in one process, 11.8 s in 8 and 7.7 s in 24) and posts all results and errors with `backtestRuns.engine.completeMany` (one outcome per run; same checks and stats recomputation as `complete`), split under 900 KB per request. So a claimed batch costs one claim request and one or more delivery requests.

Differences: when a comparison run completes, the API compares the Nautilus result (with the API's own recomputed stats) with `comparison.typescript`: the trade count, the first trade that differs in entry bar, exit bar or exit reason, and total return, Sharpe and max drawdown with the [parity tolerances](#parity-tolerances) (1e-5, 1e-3, 1e-5). It stores `report.differences = {ok, items[]}`.

Report for the owner (from the stored data): per feature, where it ran (`comparison.typescript.host`, `engineRun.host`), wall time p50/p95 over 20 runs (`typescript.wallMs` and the page round trip; `engineRun.wallMs`), queue wait, CPU (`engineRun.cpuMs`), GPU (not used) and the differences.

Pages: the instant backtest shows "TypeScript · host · round trip" at once and a Nautilus card that follows the group until its run is done (queued, running, engine time and queue wait, then a match or differences badge with the list). The sweep shows a summary line and a Nautilus column in the ranked cells. An Autopilot campaign shows a Nautilus check per gated candidate.

## Order and fill model

Nautilus matches every order and keeps the cash and position ledger. The model gives the same rules as the TypeScript engine:

- Each bar is fed as three one-minute bars: the open print, the path from the open to the low, and the path from the low to the high and the close. The low comes before the high.
- Stop first (the TypeScript rule): a bar that reaches the stop exits at the stop, also when it opens beyond the target. The target order rests during a bar only when that bar's low stays above the stop. The strategy reads the coming bar's low for this execution rule only; signals never read it.
- Signals use data up to the close of bar i. Entries and signal exits are market orders at the open print of bar i + 1.
- An entry places a reduce-only stop-market order and, under the stop-first rule, a reduce-only market-if-touched order. A level touched inside the bar fills at the level. A level gapped through fills at the open.
- Stop management (a definition's `management`, see [strategy definitions](strategy-definitions.md#stop-management-and-leverage)): at the close of every bar with an open position the strategy computes the raised stop like TypeScript `manage` (breakeven at entry + `breakevenR` × R, trail at the highest close − `multiple` × ATR once the high reaches entry + `activateR` × R, never lower). It modifies the resting stop-market order at the next open print, before any other price of that bar; nothing trades between that close and this open, so this equals a change at the close. A bar that opens at or below the raised stop exits at the open (TypeScript fills min(open, stop)).
- Leverage (`sizing.maxLeverage` with `riskPct`): the position cost is capped at cash × `maxLeverage`, as in TypeScript. The venue is a cash account with `allow_cash_borrowing`, so the borrowed part shows as negative cash; no financing is charged (the LD34 study runner charges it in research).
- Ruin (as TypeScript `runSignalBacktest`): when unit equity marked at a close is at or below 0, a market order closes an open position at that close print (reason `stop`) and the strategy places no further entries. That bar's equity is the cash after the fill.
- Short side (`side: "short"`, see [strategy definitions](strategy-definitions.md#short-side)): the entry is a market sell and the exit a market buy, so the NETTING position is short and the cash account (cash borrowing allowed) holds the sale proceeds; unit equity is balance + position × close. The stop is a reduce-only buy stop-market above the entry and the target a reduce-only buy market-if-touched below it; the stop-first rule reads the coming bar's high instead of its low. Sizing is that of a long of the same notional.
- Market on close (an `intraday` block, see [strategy definitions](strategy-definitions.md#intraday-sessions-intraday)): the compiled close mask (`Compiled.close_at`, TypeScript `closeAt`) is 1 on the last regular bar of each session day. At the close print of such a bar an open position exits with a market order, which Nautilus fills at that close print (exit reason `sessionClose`, the same path as the ruin exit); the bar counts as held and takes no entry. On an early-close day the last regular bar present is that bar.
- Entry window and decision grid: the compiled signals already carry the intraday gates (entries only in [`entryFrom`, `entryTo`] on the `decisionEvery` grid, exit conditions only on the grid); stops and targets stay live on every bar.
- `volTarget` sizing (`Compiled.leverage`): the position cost is cash × the leverage at the signal bar; a missing leverage (NaN) blocks the entry, as a missing stop distance does.
- An open position closes at the last close (exit reason `end`).
- The fee model charges the flat `costBps`, half the spread, the slippage, the commission and the fees in USD. Nautilus fills at the reference price; the trade record shows the cost-adjusted price.
- One CFD instrument with 9-decimal prices and quantities, so fractional units match the TypeScript sizing.

Known differences: Nautilus books fees in whole cents, and prices and quantities have 9 decimals. Both stay inside the parity tolerances.

Model version: every result carries `modelVersion` (`MODEL_VERSION` in `nautilus_backtest/engine.py`), raised whenever the order or fill model changes. Version 2 added stop management (the stop modify at the next open), `maxLeverage` sizing and the ruin rule, and `normalize_definition` now rejects unknown keys like the strict TypeScript schema. Workers on the research hosts must run version 2 before definitions with `timeframe`, `breaksAbove`/`breaksBelow`, `oncePerLevel`, `entry.any`, `management` or `maxLeverage` are queued: version 1 code ignores most of those fields and would return results that look valid but are wrong. Version 3 added the short side (sell entry, buy stop above, buy target below), the market-on-close exit of an `intraday` block and `volTarget` leverage sizing; `normalize_definition` accepts `side`, `intraday`, the session indicators and `volTarget` and refuses them with the TypeScript messages. Version 2 workers reject those keys as unknown, so they fail such runs rather than mis-run them; still deploy version 3 before queueing them. Nothing in the API checks `modelVersion` yet, so deploy the worker first.

## Academy on Nautilus (option instruments)

Switch plan step 6 (owner decision 2026-11-08): the Academy's modelled Black-Scholes option quotes feed Nautilus OptionContract instruments. The rules are those of `packages/academy/src/backtest.ts` (ported in `nautilus_backtest/academy/simulator.py`); Nautilus matches every order and keeps the cash and position ledger. The option prices stay modelled: there are no historical option quotes.

- Venue and account: one simulated venue, a cash account in USD with the run capital, netting, cash borrowing allowed (a short option books its premium as cash, as in TypeScript).
- Instruments: the underlying as an Equity (stock legs trade it in shares) and one OptionContract per kind, strike and expiry that the structure trades (multiplier 100, whole contracts, 9-decimal prices).
- Quotes: for every bar on which a contract is opened, held or closed, a QuoteTick with bid = ask = the modelled Black-Scholes price of that bar (the intrinsic value at or after expiry). The volatility is the supplied series (VIX for SPY) or the trailing 20-day realized volatility times `ivMult`, as in TypeScript.
- Two passes: a first pass of the same rules on a float ledger finds which contracts the run trades, because instruments and quotes must be loaded before Nautilus runs. The second pass decides again from the Nautilus account. If it needs a contract the first pass did not list, the run fails instead of trading something else.
- Order of a bar (six timestamps 1 ns apart): mark quotes of the held contracts; the decision, where the closing market orders fill at those quotes; entry quotes of the contracts opened on this bar; the opening market orders; mark quotes of the opened contracts; the mark (equity = account balance + net position × multiplier × quote, read from Nautilus).
- Entry quote and mark quote differ on the opening bar when the expiry date is not a bar day: TypeScript fills an opening leg at the price for the rule's days to expiry and marks it with the expiry snapped back to the last bar on or before that date. Both quotes are fed, in that order.
- Costs: the fee model charges the TypeScript cost of each leg ($ per contract plus slippage of the premium; stock: 0.5 cent per share plus 5 bp) as commission. An expired option settles at its intrinsic value without a fee: the strategy closes it with a market order at the intrinsic quote on the settlement bar. No early assignment and no exercise into shares.
- Expiry: a contract's `expiration_ns` is its modelled expiry, or 5 ns after the bar on which the rules settle it when that is later (the first bar at or after the expiry). Nautilus's own expiry processing therefore never finds an open position.
- Sizing reads the Nautilus account balance (the book is flat when the rules size a new position).
- Deterministic: the same input gives the same result; no random fill model, no network.

Parity: the 19 structures run on three synthetic daily series (66 runs: 57 with the default rules and 9 rule variants; plus 2 input-error cases) in `services/research/tests/test_nautilus_backtest_academy.py` against the TypeScript fixture, with the [parity tolerances](#parity-tolerances): the same trades in the same order (bars, exit reason, role, legs with strike and expiry, units), every leg fill within half a price tick (0.5e-9) of the modelled price, equity within 1e-5 at every bar (largest seen 1.5e-6), Sharpe within 1e-3, total return and max drawdown within 1e-5, and the same input-error messages. Known differences, as for the equity engine: Nautilus books fees and cash flows in whole cents and prices have 9 decimals. The trade records carry the Nautilus fill prices and the unrounded modelled fees. The float-ledger port alone (no Nautilus) matches TypeScript to 1e-9.

Dual run: an Academy comparison run is a backtest run with the rule `{"kind": "academy", "structure", "rules", "iv"?}` and `initialCapital` as the capital; only the Nautilus worker runs it (the TypeScript run executor fails it with "An Academy run needs the Nautilus research worker", and `backtestRuns.create` does not accept the rule). The worker result has the engine result shape, so storage, the statistics check and the differences are those of the other dual-run features. Both sides use the same mapping (`packages/api/src/academy-engine-result.ts`, `nautilus_backtest/academy/result.py`):

- unit equity: 1 on the warm-up bars (the Academy engine starts at bar 20), then dollar equity / capital. An equity at or below 0 has no engine result: such a request queues nothing.
- one trade per closed role (position, cycle or core) with its entry and exit bar; `entryPrice` and `exitPrice` are the underlying closes at entry and exit, `units` and `pnl` are per unit of capital, `netReturn` is the P&L over the absolute entry cash.
- exit reason: `profit-target` → `target`, `stop` → `stop`, `end` → `end`; `exit-dte`, `expiry` and `core-roll` → `signal` (the engine result has no finer reason; a wrong reason among those three still shows in the equity, because only an expiry is free of fees).
- statistics: `summarize` on that equity and those trades. `exposure` counts the bars of every trade, so a structure with a core and a cycle counts its bars twice.

Model version: an Academy result carries `modelVersion` from `ACADEMY_MODEL_VERSION` in `nautilus_backtest/academy/engine.py` (1), raised whenever its order, quote or fill model changes. Deploy the worker before the web app: an older worker fails an Academy rule as an unknown rule, it does not mis-run it.

## Parity tolerances

Every case must give the same trades (entry bar, exit bar, exit reason, same order), fill prices within 1e-6 (relative), unit equity within 1e-5 (relative) at every bar, Sharpe within 1e-3, and max drawdown and total return within 1e-5. An input error must give the same message in both engines.
