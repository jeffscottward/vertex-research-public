# EGM Zoom-Out Review Report

1. **[Blocker] Inconsistent rolling-window math and hardcoded lookback text when reusing `packages/api/src/openbb-iv-standing.ts`**
   - **Affected Scope:** `Architecture and contracts -> 2. Rolling calculation`, lines 112–135; `Overview`, line 22.
   - **Deficiency:** The design claims 100% parity with `openbb.volContext.ivOneYear` by calling `openbbEvaluateOwnIvBasis` and `openbbEvaluateProxyIvBasis` (`packages/api/src/openbb-iv-standing.ts`), but introduces two concrete contradictions:
     1. `openbbEvaluateOwnIvBasis` (`packages/api/src/openbb-iv-standing.ts` (lines 64-80)) slices the newest 252 table rows *first* (`rows.slice(-252)`) and then drops `atmIv30d === null`, whereas the design (lines 122–126) filters out `atmIv30d === null` *first* across all `requiredSessions` rows and then takes `valid.slice(i - 251, i + 1)`. If any of the newest 252 rows has a null `atmIv30d` while older rows exist, `openbbEvaluateOwnIvBasis` and the rolling loop disagree on both availability and window contents.
     2. `openbbEvaluateProxyIvBasis` (`packages/api/src/openbb-iv-standing.ts:156`) hardcodes `(${values.length} in 420d window)` (matching `VOL_INDEX_LOOKBACK_DAYS = 420` in `packages/api/src/server/openbb.ts:54`). Reusing it unchanged with an 835-day (1Y) or 1,238-day (2Y) lookback produces a factually false reason string.
     Additionally, creating a separate a new helper file (resolved in `packages/api/src/openbb-iv-standing.ts`) duplicates the `OPENBB_VOL_INDEX_PROXY` lookup, basis fallback, and combined-reason assembly already in `packages/api/src/openbb-iv-standing.ts` (lines 179-248) (while a third legacy helper `openbbIvPercentile` already lingers in `packages/api/src/server/openbb.ts:136`).
   - **Recommended Fix:** Keep rolling and latest 1-year IV standing evaluation in `packages/api/src/openbb-iv-standing.ts` using a single shared basis-selection and window-evaluation path with identical null-row semantics, and parameterize or remove the hardcoded `"420d window"` text in `openbbEvaluateProxyIvBasis`.

2. **[Major] Reinventing `OpenbbGateway` and coupling an OpenBB chart inside the QuantData `OptionsAnalyticsPanel`**
   - **Affected Scope:** `3. UI & Visualization`, lines 148–153; `Portal mounting points`, lines 170–178; `Risks and mitigations`, line 202.
   - **Deficiency:** `apps/web/src/features/openbb/gateway.ts` (lines 15-43) already provides `OpenbbGateway` and `createBrowserOpenbbGateway()`, and `StockDetailWorkspaceProps` (`apps/web/src/features/stock-detail/stock-detail-workspace.tsx:448`) already accepts `openbb?: OpenbbGateway`. Introducing a separate `IvHistoryGateway` + `createBrowserIvHistoryGateway()` (lines 151, 173) *alongside* adding `ivHistory` to `OpenbbGateway` (line 177) duplicates the client gateway abstraction for the same RPC. Furthermore, nesting `IvRankHistoryPanel` inside `OptionsAnalyticsPanel` (`apps/web/src/components/portal/options-analytics-panel.tsx` (lines 559-686)) mixes an OpenBB/Cboe panel into a section explicitly titled `"QuantData · research only"` (`options-analytics-panel.tsx:609`), forces prop-drilling a second gateway through `ChartsWorkspace` (`apps/web/src/components/portal/charts-workspace.tsx` (lines 676-684), which has no `openbb` prop) and `StockDetailWorkspace` (`stock-detail-workspace.tsx:598`), requires carefully placing it outside QuantData's error branch, and creates the exact PR #410 merge-conflict risk cited on line 202.
   - **Recommended Fix:** Remove `IvHistoryGateway` / `createBrowserIvHistoryGateway()` and type `IvRankHistoryPanel`'s prop as `gateway?: Pick<OpenbbGateway, "ivHistory">` (defaulting to `createBrowserOpenbbGateway()`). Mount `IvRankHistoryPanel` as a sibling of `OptionsAnalyticsPanel` in `StockDetailWorkspace` (reusing its existing `openbb` prop) and `ChartsWorkspace` (matching how `JevVerdictPanel` is already mounted as a sibling at `charts-workspace.tsx` (lines 1152-1156)). This leaves `options-analytics-panel.tsx` untouched, eliminates the PR #410 conflict, and isolates OpenBB from QuantData failures by construction.

3. **[Major] `/lab/markets` wiring assumption does not match existing lab architecture**
   - **Affected Scope:** `Portal mounting points`, lines 179–180; `Testing and verification plan`, line 190.
   - **Deficiency:** The design states it will add `/lab/markets` fixtures and update `apps/web/src/lab/entries/lenses.test.tsx`, assuming `/lab/markets` renders `OpenbbMarketsSection`. In reality, `apps/web/src/lab/entries/lenses.tsx` (lines 246-257) mounts only `<MarketContextPage />` — it does not render `<OpenbbMarketsSection />` (which is mounted separately as a sibling in `apps/web/src/app/(portal)/markets/page.tsx:19`), and no lab `OpenbbGateway` fixture exists in `apps/web/src/lab/`. Likewise, `apps/web/src/lab/entries/charts.tsx` (lines 112-117) mounts `StockDetailWorkspace` without an `openbb` gateway.
   - **Recommended Fix:** Scope lab verification to `/lab/stock` and `/lab/charts` (supplying a minimal `Pick<OpenbbGateway, "ivHistory">` fixture to `StockDetailWorkspace` and `ChartsWorkspace`) and omit `/lab/markets` OpenBB scaffolding from this card — or explicitly scope the work of adding `OpenbbMarketsSection` and a full fake `OpenbbGateway` to `lenses.tsx`.

4. **[Major] YAGNI scope creep in contract surface, multi-horizon server refetching, `asOf`, and MCP/agent-key registration**
   - **Affected Scope:** `Overview`, line 21; `Terms`, line 39; `1. oRPC contract`, lines 56–110; `2. Rolling calculation`, lines 115–119; `3. UI & Visualization`, line 155; `Testing and verification plan`, lines 187, 189.
   - **Deficiency:** For chart O20 ("Today's IV vs its 1-year range, as a line"), the API design bundles four speculative additions:
     1. **MCP tool `openbb_iv_history` and `AGENT_API_KEY_READ_PROCEDURES` registration (lines 21, 108–109, 187):** Sibling `vertex-flow-viz-gap` chart procedures (`flow.tapeSpeed`, `flow.hedgingPressure`, `flow.putCallRatio`) are explicitly excluded from `AGENT_API_KEY_READ_PROCEDURES` (`packages/api/src/server/flow.test.ts:542,693,867`) and `packages/api/src/server/mcp.ts`. Agents already have `openbb_vol_context` (`packages/api/src/server/mcp.ts:647`) for 1-year IV standing.
     2. **Four server-fetched horizons (`63`/`126`/`252`/`504`) with client stale-response race protection (lines 57, 116, 155, 189):** Supporting `2Y` (`504` points) forces querying `755` rows (~1,238 calendar days) and adds multi-horizon refetch state + race-condition handling to slice a tiny array.
     3. **Unused `asOf` input parameter (line 65):** None of the three UI surfaces (`/stock`, `/charts`, `/markets`) expose a date picker or pass `asOf`.
     4. **Redundant payload fields in `OpenbbIvHistoryOutputSchema` (lines 76–90):** `requestedSessions` echoes the input; `latest` duplicates `points.at(-1) ?? null`; top-level `asOf` duplicates `latest?.date ?? null`; and top-level `windowSessions`/`minSessions` repeat the literal `252` already present on both `own` and `proxy`.
   - **Recommended Fix:** Keep `openbb.ivHistory` portal-only (do not register an MCP tool or add it to `AGENT_API_KEY_READ_PROCEDURES` until an agent consumer needs full arrays); remove unused `asOf` and redundant output fields (`requestedSessions`, `latest`, duplicate top-level `asOf`/`windowSessions`/`minSessions`); and fetch a single 1-year (`252`-session) series (slicing `3M`/`6M`/`1Y` purely client-side if shorter horizons are desired, deferring `2Y`).

5. **[Major] Over-engineered bespoke interactive SVG chart diverging from existing portal chart conventions**
   - **Affected Scope:** `3. UI & Visualization`, lines 141–165; `Testing and verification plan`, lines 188–189.
   - **Deficiency:** The design layers four interaction/accessibility mechanisms onto a hand-rolled SVG: custom pointer-move nearest-point hit-testing with a crosshair, custom keyboard date-scrubbing (`ArrowLeft`/`ArrowRight`/`Home`/`End`/`Escape`), per-series toggle buttons with a last-series guard, and a collapsible `<details>` table of milestone sessions. Cross-checking `apps/web/src/components/portal/` shows zero existing custom SVG charts implement `onPointerMove`/`onMouseMove` crosshair scrubbing or arrow-key date scrubbing (crosshair scrubbing exists only via KLineCharts in `features/charts/chart-workstation.tsx`, and arrow-key handlers in `components/portal/` are solely for tablists). Sibling `vertex-flow-viz-gap` charts (`flow-hedging-pressure-panel.tsx` (lines 130-173), `flow-put-call-ratio-panel.tsx`, `flow-tape-speed-panel.tsx`, `breadth-90-chart.tsx`) use straightforward responsive SVGs (`vectorEffect="non-scaling-stroke"`) paired with KPI summaries and an ARIA label / accessible table. In addition, line 160 assigns `role="img"` + `tabIndex={0}` while attaching interactive arrow-key controls, which conflicts with ARIA semantics (`img` is a non-interactive role).
   - **Recommended Fix:** Follow the codebase's established portal SVG chart pattern (`flow-hedging-pressure-panel.tsx`, `breadth-90-chart.tsx`): render the responsive dual-line SVG with shaded 80/20 bands, 50 midline, latest KPI readout strip, ARIA summary, and a simple accessible table (visually hidden or compact `<details>`). Defer custom pointer/keyboard scrubbing and series-hiding toggles until actually requested (or use KLineCharts if interactive crosshair scrubbing is required).

6. **[Major] Guaranteed-empty Postgres RPC fired on every non-Core-7 ticker on `/stock` and `/charts`**
   - **Affected Scope:** `2. Rolling calculation`, lines 117–119; `3. UI & Visualization`, lines 164, 172–175.
   - **Deficiency:** In production, `cboe-option-iv` only collects `CORE7` (`services/openbb/vertex_openbb/jobs/cboe.py:323`: `for symbol in ctx.symbol_list(CORE7):`), and `OPENBB_VOL_INDEX_PROXY` (`packages/api/src/contracts/openbb.ts` (lines 93-104)) only maps those same 7 ETFs (`SPY`, `QQQ`, `DIA`, `IWM`, `GLD`, `SLV`, `USO`). Mounting `IvRankHistoryPanel` unconditionally on every US stock on `/stock/<symbol>?tab=analytics` and `/charts?symbol=<symbol>` fires an HTTP request and a Postgres `row_number() over (...)` query (`packages/db/src/server/openbb.ts` (lines 1007-1030)) on every single non-Core-7 equity (e.g., `NVDA`, `AAPL`, `MSFT`) just to render a permanent unavailable empty state.
   - **Recommended Fix:** Either render the panel (or issue the RPC) only for `OPENBB_CORE7` tickers (with a lightweight client-side note or omission for uncollected equities until `openbb_option_iv_daily` collects broader underlyings), or explicitly document in `Overview` why non-Core-7 stocks are expected to receive `openbb_option_iv_daily` rows soon enough to justify the query on every load.
