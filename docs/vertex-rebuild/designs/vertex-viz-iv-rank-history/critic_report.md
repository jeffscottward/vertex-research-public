# Deficiency Report — `docs/vertex-rebuild/designs/vertex-viz-iv-rank-history/design.md`

1. **Severity:** Blocker
   - **Affected Scope:** `design.md` §2 lines 117, 120–130; `packages/api/src/openbb-iv-standing.ts` lines 61–118; `packages/db/src/server/openbb.ts` lines 1007–1031.
   - **Deficiency:** Null `atmIv30d` gap handling contradicts `openbbEvaluateOwnIvBasis` and under-fetches via `optionIvDaily`.
     - `openbbEvaluateOwnIvBasis` slices the newest 252 *stored* rows (`rows.slice(-252)`) and rejects the window (`ivPercentile: null`) if *any* row in those 252 rows has `atmIv30d === null`. In contrast, `design.md` lines 121–128 strips `atmIv30d === null` rows *before* building 252-observation rolling windows. When an interior null exists outside the newest 252 rows, `openbb.ivHistory` selects `own_atm_iv` and plots historical dates using 253+ calendar-session windows that span the null — directly contradicting `openbb.volContext({ asOf })` and `openbb.ivHistory({ asOf })` for those exact dates (which return `own.ivPercentile: null`).
     - Additionally, `openbb.optionIvDaily([symbol], asOf, requiredSessions)` (`packages/db/src/server/openbb.ts` (lines 1007–1031)) caps total rows (`row_number() <= sessions`) *including* `atm_iv_30d IS NULL` rows. If `k` of the newest `requiredSessions` rows are null, the query returns `requiredSessions - k` valid observations and silently truncates the plotted series to `requestedSessions - k` points even when older valid rows exist in Postgres.
   - **Recommended Fix:** Align the window definition across both modules. Either (a) enforce strict 252-stored-session windows in `openbb-iv-history.ts` matching `openbbEvaluateOwnIvBasis` (skipping/breaking any date whose trailing 252 stored rows contain any `atmIv30d === null`, preserving point-in-time parity with `volContext`), or (b) if skipping interior null sessions is desired across both endpoints, update `openbbEvaluateOwnIvBasis` and add a `atm_iv_30d IS NOT NULL` query/buffer to `optionIvDaily` so both endpoints evaluate identical 252-valid-session windows while still rejecting a null latest session.

2. **Severity:** Blocker
   - **Affected Scope:** `design.md` §Overview line 21, §1 lines 64 & 95–102; `packages/api/src/server/handler.ts` lines 10–11, 137–142; `packages/api/src/contracts/openbb.ts` lines 1169–1174.
   - **Deficiency:** `OpenbbIvHistoryInputSchema.sessions` lacks numeric coercion on a `GET` route, causing HTTP 400 on OpenAPI REST calls, and the documented HTTP path is incorrect.
     - `openApiHandler` (`packages/api/src/server/handler.ts` (lines 137–142)) does not mount `SmartCoercionPlugin`. Query parameters on `GET` routes arrive as strings (`"63"`, `"126"`, `"252"`, `"504"`). `z.union([z.literal(63), z.literal(126), z.literal(252), z.literal(504)]).default(252)` rejects string query values with HTTP 400 (the exact reason `OpenbbInsiderClustersInputSchema` at `contracts/openbb.ts` (lines 1169–1174) uses `z.coerce.number().pipe(...)`).
     - Line 21 documents `GET /api/rpc/openbb/iv-history`, which does not exist in this codebase (`ORPC_RPC_PREFIX` is `/api/orpc` and `ORPC_OPENAPI_PREFIX` is `/api/openapi`).
   - **Recommended Fix:** Define `sessions` as `z.coerce.number().pipe(z.union(OPENBB_IV_HISTORY_HORIZONS.map((n) => z.literal(n)))).default(252)` (with `OPENBB_IV_HISTORY_HORIZONS` typed as a non-empty tuple, matching `OpenbbInsiderClustersInputSchema`), add an OpenAPI `GET ?symbol=SPY&sessions=63` test in `openbb-server.test.ts`, and correct line 21 to `GET /api/openapi/openbb/iv-history` (oRPC path `/api/orpc/openbb/ivHistory`).

3. **Severity:** Blocker
   - **Affected Scope:** `design.md` §1 line 65, §2 line 118; `packages/api/src/contracts/openbb.ts` lines 269–283, 1010–1012; `packages/api/src/server/openbb.ts` lines 82–87, 311–312; `packages/db/src/server/market-daily-series.ts` lines 36, 137–152, 222–230.
   - **Deficiency:** Unbounded `asOf` lower bound triggers an unhandled `MarketDailySeriesInputError` (HTTP 500) on Core 7 symbols.
     - `date` in `contracts/openbb.ts` permits any 4-digit year (`0000`–`9999`). For a Core 7 symbol with `sessions = 504` (`lookbackCalendarDays = 1238`) and `asOf <= "1003-05-22"` (e.g., `"0999-01-01"` or `"1000-01-01"`), `nyDate(-1238, asOf)` produces a year `< 1000` or negative ISO date. `series.loadSeries` enforces `ISO_DATE_PATTERN = /^([1-9]\d{3})-(\d{2})-(\d{2})$/u` and throws `MarketDailySeriesInputError`, which read handlers in `server/openbb.ts` do not catch.
   - **Recommended Fix:** Reuse `historyFrom.optional()` (`>= "1900-01-01"`, already defined at `contracts/openbb.ts:1010`) for `asOf` so `asOf - 1238d` always stays well above year 1000, and defensively catch `MarketDailySeriesInputError` to return `errors.BAD_REQUEST`.

5. **Severity:** Major
   - **Affected Scope:** `design.md` §Method line 46, §2 lines 129–135.
   - **Deficiency:** Automatic basis switchover at day 252 creates a multi-month history collapse for Core 7 ETFs with no disclosure or fallback control.
     - On day 251 of `openbb_option_iv_daily` collection, `SPY` (`1Y`/`2Y`) renders 252 or 504 daily points via the Cboe `VIX` proxy. On day 252, `own.ivPercentile !== null && ownPoints.length > 0` becomes true and unconditionally switches `basis` to `own_atm_iv` with **`points.length === 1`**, collapsing every Core 7 `1Y`/`2Y` chart into a single dot for months until `own_atm_iv` reaches 503–755 stored sessions. The design provides neither a `"Showing N of M requested sessions"` indicator nor an opt-in basis selector to inspect the multi-year Cboe index proxy during the transition.
   - **Recommended Fix:** (a) Always surface actual vs requested plotted sessions in the chart header/subtitle when `points.length < requestedSessions` (e.g., `"Showing 14 of 252 sessions (own ATM IV history starts YYYY-MM-DD)"`); and (b) consider adding an optional `basis?: "auto" | "own_atm_iv" | "vol_index_proxy"` input (default `"auto"` matching `openbb.volContext.ivOneYear`) and UI basis toggle whenever both bases qualify (`>= 252` sessions) so operators keep multi-year context without ever mixing the two series.

6. **Severity:** Major
   - **Affected Scope:** `design.md` §2 lines 118, 131–133; `packages/api/src/openbb-iv-standing.ts` line 156.
   - **Deficiency:** Reusing `openbbEvaluateProxyIvBasis` emits a false `"in 420d window"` diagnostic string.
     - `openbbEvaluateProxyIvBasis` (`openbb-iv-standing.ts:156`) hardcodes `Needs 252 sessions of ${index} (${values.length} in 420d window)`. In `openbb.ivHistory`, `lookbackCalendarDays` is `Math.ceil(requiredSessions * 1.6) + 30` (533d for 3M, 634d for 6M, 835d for 1Y, 1,238d for 2Y). Calling `openbbEvaluateProxyIvBasis` unchanged causes `proxy.reason` and top-level `reason` to misreport the queried window as `420d`.
   - **Recommended Fix:** Add an optional `lookbackDays = 420` parameter to `openbbEvaluateProxyIvBasis` so `openbb.volContext` keeps `"420d window"` while `openbb.ivHistory` passes `lookbackCalendarDays`.

   - **Deficiency:** Unbounded MCP context footprint for `openbb_iv_history` at `sessions: 504`.
     - Returning 504 six-field point objects directly in MCP JSON emits ~55–65 KB (~15k tokens) in a single tool call. Other high-row-count tools in `mcp.ts` and `research-tools.ts` (`openbb_congress_trades`, `openbb_smart_money_ranking`, `openbb_insider_clusters`, `backtest_runs_get`, `drift_monitor_get`) define `present` formatters to keep agent context bounded, whereas `design.md` specifies no `present` strategy or payload budget for `openbb_iv_history`.

10. **Severity:** Major
    - **Affected Scope:** `design.md` §Method line 47; `packages/db/src/schema/openbb.ts` lines 167–188; `packages/db/src/server/openbb.ts` lines 1007–1031.
    - **Deficiency:** Inaccurate table/index claim masks a missing `(underlying, as_of)` index on `openbb_option_iv_daily`.
      - Line 47 attributes PK `(series_id, date)` to `market_daily_series` (actually `market_daily_points`; `market_daily_series` is metadata keyed by `id`).
      - More importantly, `openbb_option_iv_daily`'s only index is its composite PK `(as_of, underlying)` (`packages/db/src/schema/openbb.ts:187`), where `as_of` is the leading column. `optionIvDaily([symbol], asOf, requiredSessions)` filters `underlying IN ($1) AND as_of <= $2` and orders by `(underlying, as_of DESC)`, forcing a wide scan over all underlyings for every `/stock/<symbol>` and `/charts` request (including tickers with zero rows).
    - **Recommended Fix:** Fix the table name to `market_daily_points`, acknowledge the `(as_of, underlying)` PK leading-column mismatch, and either add a non-breaking secondary index on `openbb_option_iv_daily (underlying, as_of DESC)` or document an explicit row-count threshold for adding it before expanding beyond Core 7.
