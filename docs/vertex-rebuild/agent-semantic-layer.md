# Agent semantic layer: decision on NVIDIA Auto Ontology

Updated: 2026-11-15 (Q19, Q20 and H4 recorded again after the fixture baseline runs got a profit factor, an equity series and a losing streak; 9 questions recorded again after migration 0075; 11 after migration 0074; recording format with model and date per trial; build 2026-11-08). Cards `vertex-agent-semantic-layer` (decision) and `vertex-semantic-layer-build` (build). Research only. Nothing here gives an agent permission to place, approve or change a trade.

## Decision

**Option (b): build the pattern natively in Vertex. Do not adopt NVIDIA Auto Ontology as a service (option a).**

The native layer is a small catalog of certified business terms plus two read-only tools (`list_terms`, `query_term`). Each answer returns the value, the exact SQL or live-feed path, the rows and the certification state. The model chooses a term and its parameters. The model never writes SQL.

Reasons:

1. **The most important terms are not in Postgres.** Net liquidation, P&L and live positions come from the `vertex-portfolio` feed (`packages/api/src/contracts/portfolio-monitor.ts`). Auto Ontology queries databases only, so it cannot answer the questions that carry the most risk.
2. **The current assistant gives wrong account numbers today.** In the prototype, the current tool set answered 23 of 24 account questions (Q1-Q8, three trials each) with numbers from the paper exec node, because `deployment_status` is the only account-like tool it has. The semantic layer answered all 24 correctly.
3. **Free text-to-SQL picks the wrong table.** The text-to-SQL arm (the approach Auto Ontology automates) gave 6 confident wrong answers, all on backtest metrics, where it read agent notebook records instead of engine runs. The semantic layer gave 0 wrong answers.
4. **Auto Ontology does not enforce its certification at query time.** The `certified` flags are UI badges and search filters; the text-to-SQL path does not read them (see the facts below).
5. **Cost and attack surface.** Auto Ontology adds six Compose services, its own Postgres with pgvector, an embedding endpoint and unauthenticated ports. Vertex already has an MCP server, oRPC, Drizzle and a tool loop that can carry two more read-only tools.

Auto Ontology remains a useful reference for the term data model (term, synonyms, certified SQL attribute, join path) and for the MCP answer shape (`answer`, `sql`, `rows`, `row_count`, `truncated`).

## Facts: Vertex today

- The operator assistant calls a fixed list of oRPC-backed MCP tools (`packages/api/src/server/assistant-runtime.ts:56-127`, `packages/api/src/server/mcp.ts:204-531`, `packages/api/src/server/research-tools.ts:62-113` for `drift_status`). No tool runs model-written SQL.
- No assistant tool reads the `vertex-portfolio` feed. `deployment_status` returns the QuantVPS exec-node snapshot, which has its own `equity.net_liq`, positions and P&L (`DeployEquityBlockSchema` in `packages/api/src/contracts/agent-ops.ts:1127-1136`). Paper deployment requests are paper-only by a check constraint (`deployment_requests.mode = 'paper'`).
- Backtest metrics live in two places with different meanings and units. Engine runs: `backtest_runs.report.metrics.sharpe` and `maxDrawdownPct`, which holds a positive fraction despite its name (0.2 = 20%; `packages/api/src/backtest-run-report.ts:108-121`). Agent records: `backtest_results.metrics` (free-form keys such as `sharpe_ratio` or `Sharpe`) and `max_drawdown` (negative fraction).
- Gate outcomes: `autopilot_candidates.status` is `evaluated` (not yet judged), `rejected` (failed `autopilot-gate-v1`) or `verified` (passed). `fitness` is in-sample Sharpe; `oos_sharpe` is out-of-sample.
- Crown copy-book legs have no data in Vertex. `crownCopy` is only an input flag of the risk allocator (`packages/api/src/contracts/risk-allocator.ts:36-48`).
- "Open risk" has no table or field. Owner decision (2026-11-05): the certified term `open_risk` is the sum of the defined maximum loss of each open option structure (debit paid for long options and debit spreads; width minus credit for defined-width credit spreads). This is a research definition only. It changes no trade or risk setting.

## Prototype

The prototype is throwaway. Its purpose is to settle the decision above.

### Setup

- **Database:** a non-production database on the rig (`darkfactory_test_semantic_layer_proto`, local Postgres 17.6) built from the real migrations `0000`-`0048` and the synthetic [fixture.sql](agent-semantic-layer/fixture.sql). All names and numbers are invented. No production or account data was copied, and no data left the rig except synthetic rows sent to the model.
- **Read-only:** every query ran with `default_transaction_read_only=on` and a 5-second statement timeout. A test `DELETE` failed with "cannot execute DELETE in a read-only transaction".
- **Live feeds:** synthetic `vertex-portfolio` (live account, NLV 248,350.12) and `deployment_status` (paper exec node, `net_liq` 100,412.55) payloads in the shapes of the Vertex contracts.
- **Model:** the same Claude model for all arms through OMP `completion()` (subscription; no new provider), with the rules of the Vertex assistant system prompt, a JSON tool-call loop, 8 steps and 16,000-character tool results.
- **Arms:**
  - **A, current:** emulated current read tools: `strategies_list/get`, `backtests_list/get`, `backtest_runs_list/get`, `drift_status`, `deployment_status`.
  - **B, text-to-SQL:** `list_tables`, `describe_table`, `run_sql` on the database only. This is a proxy for option (a) without Auto Ontology's glossary. Auto Ontology itself was not run, because it needs an embedding endpoint that the Claude-only routing does not have.
  - **C, semantic layer:** arm A tools plus `list_terms` and `query_term` over the 10 terms below.
- **Grading:** a Claude grader with a fixed rubric (correct, wrong, declined), then a manual audit. Two grades were changed in the audit; both are listed in [eval-results.json](agent-semantic-layer/eval-results.json) under `overrides`. "Declined" means the answer said the data was unavailable and gave no wrong value.

### What the numbers show

- **Wrong-account answers are the largest risk today.** Arm A answered account questions with the paper exec node's numbers in 23 of 24 main trials and 8 of 9 held-out trials. Most answers named the paper account in the text, but still gave the paper value as the answer.
- **Text-to-SQL refuses account questions but picks the wrong source for metrics.** Arm B wrote correct SQL for gates, requests and drift, but used notebook records (`backtest_results`) for Q14 and Q16, and so gave 6 wrong answers.
- **The semantic layer removes both errors in this test.** Arm C had 75 of 75 correct trials, including three questions (Q9, Q10, H5) where the right answer is "not available".
- **Units are a trap for agents too.** The first version of this prototype treated `maxDrawdownPct` as a percent because of its name. A fresh-context review found that the engine stores a fraction. The fixture and the term were fixed, and Q13-Q16 were run again for all arms; the tables show the second run. A certified term records the unit once, so each agent does not have to infer it.

### Limits of this evidence

- The same agent wrote the terms, the questions and the reference answers. The held-out set reduces this bias but does not remove it. The test shows that the tool shape prevents the observed errors; it does not show that 10 terms cover the owner's real questions.
- The data and feeds are synthetic. Real feeds can be stale or unavailable; the real build must return "unknown" in that case.
- Arm A emulates the current tools against the fixture. It is not the deployed assistant (which uses `VERTEX_ASSISTANT_MODEL` through OpenRouter).
- One model family and three trials per cell. The grader is a model, checked by a manual audit.
- The owner certified `open_risk` on 2026-11-05, after these trials ran. `eval-results.json` records it as `certified: false` because it is a record of that run.

Artifacts: [fixture.sql](agent-semantic-layer/fixture.sql) and [eval-results.json](agent-semantic-layer/eval-results.json) (questions, references, terms, every answer, tool calls and grade). The harness ran in an OMP eval session and is not part of the product.

## Recommended build (follow-up card)

Follow the feature workflow in `AGENTS.md` (contract first, failing test, 100% coverage).

1. **Contract:** oRPC `semanticTerms.list` and `semanticTerms.query({ term, params })` with Zod parameter schemas per term. Output: `{ term, certified, source: "postgres" | "feed", query, rows, asOf, answer, status: "ok" | "unknown" | "not_available" }`. `query` is the SQL text or the feed path.
2. **Catalog:** a reviewed TypeScript module, one entry per term. SQL terms call Drizzle repository functions in `packages/db`; the returned `query` text comes from the Drizzle query (`toSQL()`), not from a model. Feed terms read the existing portfolio-monitor service. A stale or unavailable feed returns `unknown`, never zero.
3. **Tools:** add `terms_list` and `terms_query` to `MCP_TOOLS` as read-only tools; they are then available in Plan mode. Do not add a raw SQL tool.
4. **System prompt:** tell the model to use a certified term when one exists, and to say "not available" when none exists.
5. **Interim fix in the same card:** change the `deployment_status` tool description to state that its equity, positions and P&L belong to the exec-node account named in `session.trading_mode`, and are not the owner's IBKR account summary.
6. **Owner inputs for the build:** choose a Crown copy-book data source (or keep the term as "not available"). The `open_risk` definition is certified (2026-11-05).
7. **Acceptance:** an automated test runs the 25 questions above against fixtures with a recorded model, and checks that each answer carries the certified source.

### Eval of the built layer

Method: the 25 questions above (Q1-Q20 main, H1-H5 held out), 3 trials each, through the real Plan-mode assistant turn (`runAssistantTurn`, all Plan-mode tools), the real oRPC handler, a Postgres database with all migrations plus [fixture.sql](agent-semantic-layer/fixture.sql), and synthetic feeds (`tests/integration/semantic-layer/fixtures.ts`: live account NLV 248,350.12; paper exec node net_liq 100,412.55). The model is the OMP `completion()` default model (Claude subscription, no new provider), bridged by `tests/integration/semantic-layer/record.ts`. Grading is a fixed rubric (`tests/integration/semantic-layer/questions.ts`): required values must appear and paper exec-node values must not appear anywhere in the answer. An independent grader (OMP `judge_batch`, TypeSafe `jev-1.14` model, one call per answer with the question and the reference; synthetic data only) graded all 75 answers and agreed with the rubric on every trial. Its verdicts are stored in the recording with the grader name, the instructions and the date; they are an attestation from the recording run, not recomputed in CI. Since 2026-11-20 the independent grader is `anthropic/claude-opus-5-5` with stricter instructions and the majority of three runs; see the note on the grader change of 2026-11-20 below.

|Set|Correct|Wrong|Declined|
|---|---|---|---|
|Main (Q1-Q20), 60 trials|60|0|0|
|Held out (H1-H5), 15 trials|15|0|0|
|Account questions (Q1-Q8, H1-H3), 33 trials|33|0|0|

Every account trial called `terms_query`; no trial called `deployment_status`. Mean tool calls per trial: about 1.9.

What CI proves and what it does not: the 75 answers above are a one-time result of the recording. CI does not call a model. `tests/integration/semantic-layer/eval-replay.test.ts` replays the recording (`eval-recording.fixture.json`) against the built layer in the integration lane. It checks for every trial that the messages the model was given (system prompt, question and every tool result) are unchanged, and it applies the tool rule to the tool list of the trial (see "How to record" below); a trial that fails either check is stale and must be recorded again. It regrades every answer with the rubric, and fails below 58/60 (rubric and recorded independent grade both "correct") or on any wrong account answer (by either grade). Since 2026-11-26 the replay does not prove that all three trials of a question saw the current tool list. It proves for every trial that each tool the trial calls is defined as it was at the recording, and for every question that at least one trial was answered with the current tool list and used no changed tool in it. One such trial can miss a changed tool that the model would use only in some runs.

Failed tool calls: a trial can be graded correct although a tool call failed, because the model answers from another tool or says that the data is not available. The replay therefore fails a trial in which a tool call fails, unless `tests/integration/semantic-layer/tool-failures.ts` lists the call as an expected input rejection for the question of the trial. Only a call whose arguments the layer refused can be listed: the API answered `BAD_REQUEST (400)`, or the input schema of the tool refused the arguments. A server error (5xx), a call that threw, a missing row (404) and every other failure cannot be listed; correct the layer or the fixture. To add an entry after a recording, copy the tool, the arguments and the error from the failure message of the replay, and write why the rejection is correct behavior of the layer. Remove an entry when no recorded trial makes the call any more; `tests/integration/semantic-layer/tool-failures.test.ts` fails for an entry that no trial uses. When a recorded trial has a failed call that cannot be listed and that is the model's own error (for example more tool calls in one step than a turn allows), record all three trials of the question again and give the reason in the commit. Do not record one trial again until the failed call is gone: that would remove the trials in which the model made an error.

Unknown term answers: `terms_query` does not report a failed certified SQL text, a live-account feed that cannot be used (unavailable, not live, not the live account, or a missing, stale or future data time), or a feed with no value for the term as an error. It answers `status: "unknown"` with no value, and the turn trace marks the call as a call that worked. The replay therefore also fails a trial in which a `terms_query` answer has status `unknown` (`unknownTermAnswer` in `tests/integration/semantic-layer/tool-failures.ts`; the failure message names the term input and the answer text). #### How to record

One command records: `bun run eval:semantic:record -- [--expect=<n>] [--log=<file>] [trials] [concurrency] [stale | upgrade | ids...]` (`tests/integration/semantic-layer/record-session.ts`). It starts one OMP session with the recording model (`RECORDING_MODEL` in `tests/integration/semantic-layer/recording.ts`, `anthropic/claude-opus-5-5`). That session runs the model bridge (`tests/integration/semantic-layer/bridge.ts`) in its eval tool, and the bridge starts the recorder (`tests/integration/semantic-layer/record.ts`; its header has the protocol). The recording uses the Claude subscription of the session and no other provider. Design and review: [eval-recording-cost](designs/eval-recording-cost/plan.md).

- `-- 3 4 stale` first replays every recorded trial without a model, prints the selected trials with the reason for each, and asks the model only for those. It selects every stale trial, every missing trial, and one witness trial for each question whose trials all saw an older tool list. With nothing to record it does not write the recording; it writes the master-rules freeze when its replay froze a search. `--expect=<n>` stops the run before the first model request when the selection has another size; state the number you planned. To see the selection with no model call, use `--expect=0`: `bun run eval:semantic:record -- --expect=0 3 4 stale` prints what a recording would cost and stops.
- `-- 3 4 <ids>` records the named questions. `-- 3 8` records every question; when it stored every trial it drops all other trials.
- Every run keeps the `audit` header. A run with ids or `stale` keeps every trial that it did not record. Each trial holds its own `model`, `promptFormat`, `recordedAt` and `toolList`.
- `trials` is the number of trials for each question (3). `concurrency` is the number of trials that run at the same time.

The tool rule (`toolVerdicts` in `recording.ts`): the header `toolLists` holds, for each tool list that a trial names, the digest of each tool definition.

- A trial is stale when a tool that it calls differs from the recorded definition or is gone.
- A trial that saw an older list and calls none of the tools that differ is valid only while its question has a witness: a trial that saw the current list, is valid in every other check (messages, final answer, model, prompt format, rubric grade) and calls none of those tools.
- A question with no witness needs one new trial. The recorder takes the oldest trial of the question, so three changes of the tool list record all three trials again.
- When the witness calls a changed tool, the other trials of the question are stale: run `stale` a second time.

A new tool text can be pushed for review before its recording. The pull request cannot merge before the recording, because the replay fails.

When two branches change tools at the same time, the second one to merge has a tool list that no trial saw. Merge the base first, take the recording file of the base whole, then record.

What the recorder refuses:

- **A bridge fault.** When the bridge gets no model reply after four tries, the trial is not stored and the run goes on.
- **Another model.** The bridge checks the model with one call before the start. At a reply from another model than `RECORDING_MODEL` the recorder does not store that trial and starts no further trial; a trial that is running ends as usual.
- The run then ends with exit code 1 and lists the failed trials. Each finished trial is written at once, so a failed or killed run keeps its finished trials: run `stale` again.
- A change of the recording model is a full recording: change `RECORDING_MODEL` in the commit of that recording.
- The prompt that the bridge builds is model input. `RECORDING_PROMPT_FORMAT` in `recording.ts` is the hash of that prompt for one fixed request (`tests/integration/semantic-layer/bridge.test.ts` checks it), and every trial stores it in `promptFormat`. An edit of the prompt changes the constant, makes every trial stale and is therefore also a full recording.
- **Another writer.** A program that writes the whole file during a run (a grading step that read it earlier) deletes trials of the run. The recorder reports such a trial as failed at its end.

After a run, four steps stay manual:

1. Format both fixture files with Biome: `bunx --bun --no-install biome format --write tests/integration/semantic-layer/eval-recording.fixture.json tests/integration/semantic-layer/master-rules.fixture.json`.
2. Grade the trials that were recorded with the grader and the instructions of the `audit` header (`graderModel`, `instructions`; the prompt format is in `grader-self-test.fixture.json`, the procedure in the note on the grader change of 2026-11-20 below). A trial that was recorded again has no `audit` grade, and the replay test fails until it has one. Do not write grades into the file while a recording runs.
3. Update the `audit.grader` text and `audit.gradedAt` of the header, which the recorder does not write.
4. Run `bun run test:integration`. When it names a stale trial with the reason "every trial ... recorded with the current list calls a changed tool", run `stale` again.

A recording of the older format (`schemaVersion` 2): `bun run eval:semantic:record -- 3 6 upgrade` writes the new fields with no model call for every trial that still replays (see the format note of 2026-11-26 below).
