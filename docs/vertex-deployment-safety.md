## Exact source, dependency and toolchain inputs

`approved-inputs.ts` walks raw commit/tree/blob objects with replacement semantics and promisor lazy-fetch disabled, verifies each Git object hash, and builds a deterministic complete source manifest. All Git child environments also deny transport protocols: missing objects fail rather than fetch. It rejects symlinks/gitlinks, special/unreviewed modes, traversal, case collisions, ambiguous paths, implicit dotenv/config inputs, host dependency trees and generated caches. Source limits are 20,000 tree entries, depth 32, 16 MiB per blob, 4 MiB per tree/commit and 256 MiB total file bytes. Exact Wrangler bytes and human destination/database policy are revalidated from the materialized objects.

The dependency authority digest covers the lock, workspace policy, package manifests, Node pin, preparation policy and patches. External file/link/Git/tarball acquisition is unsupported. Ordinary `workspace:*` and contained pnpm links remain supported; they are not links to this checkout. Preparation policy pins Node 22.13.1, Bun 1.3.14, pnpm 11.16.0 and linux/amd64.

The official image child-manifest pins and provenance are in `infra/docker/deployment/policy.json` and `image-provenance.json`. Registry metadata was hash-verified, not runtime binaries. Node's final base is Bookworm; the Bun executable comes from a Trixie image. The runner never copies Bun's Node-fallback shim. Exact actual binary version checks and native preparation probes must pass in the resulting image; metadata does not establish cross-base binary compatibility.

`runner-runtime.ts` reads only `private/deployment/offline-inputs/{pnpm,store}/`. This separately acquired, credentialless capsule contains a complete regular-file pnpm 11.16.0 package closure (`pnpm/bin/pnpm.cjs`) and an offline pnpm store for the reviewed lock/platform. Files are newly copied into bounded memory, checked for symlinks/hardlinks/special modes and drift, then hashed with their paths and normalized executable modes. Bounds are 100,000 files, 200,000 total entries, depth 32, 128 MiB per file and 1 GiB total. The entire digest must match the approved Git policy. A directory name, version label or mutable store mount is not accepted as identity.

The runner constructs a regular-file/directory tar and fixed preparation/guard programs centrally; it never builds the working directory or runs a source-selected Dockerfile. Both image manifests and their verified config IDs must already be local. Every create uses a content ID and `--pull=never`, including a never-started Bun donor and a credentialless, network-none preparation container. There is deliberately **no `docker build`**: its RUN-network flag would not prohibit daemon-side base fetching. A bounded parser accepts only the donor's single regular executable, not arbitrary archive extraction or links. Verified source/capsule bytes are copied through the Docker API with fixed ownership, never mounted from the host.

Preparation runs non-root with dropped capabilities. Runtime binaries, pnpm code, guard, preparation script and source manifest remain root-owned in root-owned directories; package preparation cannot replace them. Only the copied workspace/store directories and a precreated digest-output file are writable to the preparer. A frozen offline pnpm install uses byte-copy package import and initially disables scripts; only `esbuild`, `sharp` and `workerd` are rebuilt without credentials, followed by native loading/version probes. Source bytes are rechecked before sealing. The stopped container is committed to a derived content-addressed image, retaining only its own sealed inputs (including its capsule copy), not a shared cache. There is no package/image fetch, host install, shared `node_modules`, host store mount or cache reuse. Missing native output is a preparation failure.

The in-image guard verifies every source file and the full dependency tree, rejects extra nondependency files, escaping/absolute/looping/dangling links and regular files with extra hardlinks, checks reviewed official adapter/plugin/runtime versions, and records dependency/toolchain digests. A contained relative workspace/pnpm link is allowed only after complete resolution remains inside `/workspace`. It audits again in a credentialless read-only container and once more immediately before the adapter. The derived image is addressed by its Docker content ID, never by a mutable tag during execution. Preparation identity is evidence, not human approval.

The reviewed esbuild and workerd installers legitimately hardlink their native executable to a public bin path. During credentialless preparation only, a bounded inventory groups regular dependency files by device/inode and requires the entire inode link count to be accounted for inside `/workspace/node_modules` paths owned by the preparer. Source, capsule/store, foreign-owner and unaccounted outside aliases are rejected, not exempted. Every admitted alias is replaced with an exclusive no-follow independent byte copy after digest, ownership and executable-mode checks; only the created temporary inode is eligible for cleanup. The final source/full-tree audit still requires every regular file to have exactly one hardlink. Verification and adapter execution never normalize or waive post-seal links. Synthetic regressions mirror both reviewed esbuild versions and the workerd public/native package layout, including failure and alias-escape cases.

## Concrete execution, outputs and cleanup

The local backend uses `/usr/bin/docker` against `unix:///var/run/docker.sock`, with no user Docker configuration, and `/usr/bin/git` with controlled environment/configuration. Unsupported hosts or missing local daemon/images/capsule fail closed; there is no host-execution fallback. The Docker daemon is part of the trusted isolation boundary.

Execution/check containers run non-root with read-only root filesystem, dropped capabilities, no-new-privileges, process/memory/CPU/file-descriptor bounds, no host mounts/socket/home/store, closed stdin and a fixed Node/guard entrypoint. Only fresh tmpfs locations are writable: `/tmp`, app `dist`, app `.wrangler`, app `node_modules/.vite-temp`, app `node_modules/.vite`, and root `node_modules/.vite-temp`. The latter locations accommodate the pinned Vite config-loader/cache behavior without making source or dependency roots writable. A future compatibility failure does not authorize widening those mounts.

Check mode has no provider credential and network `none`. Deploy mode uses the normal official adapter build/upload operation with bridge networking and only the explicitly projected `CLOUDFLARE_API_TOKEN`; no implicit login or credential discovery is attempted. The token is not placed in argv or a host file. Docker administrators can inspect container configuration, so daemon access is privileged. Approved executable application code runs during the official build and can observe its projected deployment credential; this design does not claim credentialless build/upload separation or protection from malicious approved source.

The official invocation is fixed: production `deploy` (optionally `--dry-run`), staging the same plus `--env staging`. Production never becomes a named `--env production`. No `--skip-build`, alternate config/name, caller artifacts or raw Wrangler wrapper is allowed. Installed `@vinext/cloudflare` 1.0.0-beta.3 resolves local Vite, loads production dotenv and propagates staging for metadata/build/upload. The plugin's generated `.wrangler/deploy/config.json` exists only as this run's writable output. **Official `--dry-run` returns before building or deploying**, so a successful check proves setup only, not build readiness.

Provider stdout/stderr are bounded and discarded; container logging uses `--log-driver=none`. Structured results contain only allowlisted mode/environment, phase, bounded reason, exit status, cleanup state and whether a provider may have been reached. No environment values, destination objects, receipt text or arbitrary exceptions are serialized. No child logs or build-output tree are exported as debug artifacts.

Every container has a unique run-owned name and label. Cleanup rechecks identity and ownership before removing exact containers and the unique derived image tag; it never prunes shared resources or deletes host source/capsule files. Timeout/output overflow kills the client and cleanup force-removes owned containers. Cleanup failure returns nonzero, preserving an `uncertain` result if deployment may have started. No automatic retry is attempted. Interrupted copy/commit behavior and real process-tree termination still require the integration owner's OS-level failure probes; broad daemon pruning is forbidden.
