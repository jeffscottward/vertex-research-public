# QuantVPS exec node (`ibkr-nautilus-exec-node`)

The exec node is the Docker Compose project `ibkr-nautilus-exec-node` on QuantVPS: `ib-gateway`, `nautilus-trader` (always on, DISARMED unless the owner arms it), `watchdog`, `postgres`, `redis`, `portfolio-ui`, `caddy`, `uptime-kuma` and `netdata`. Until 2026-10-31 it ran from the vertex-quant checkout `/opt/vertex-quant`. Vertex Research now owns its definition, and the runtime root is `/opt/vertex-exec-node`.

## What this directory owns

| Path | Content |
| --- | --- |
| `runtime/` | Vertex-owned files placed into the runtime root: `docker-compose.yml`, `watchdog/`, the arm gate (`nautilus/arm_gate.py`, `nautilus/arm_cli.py`), the owner arm CLI (`runtime/scripts/nautilus-arm.sh`, run on the rig), the IBKR 2FA script with the IBKR-only readiness fix (`runtime/scripts/request-ibkr-2fa-until-ready.sh`, `runtime/scripts/ibkr_account_snapshot.py`), the account heartbeat (pm2 `vertex-ibkr-account-heartbeat`), the Nautilus down alert and their shell helpers. |
| `systemd/` | Units that name the runtime root: `vertex-nautilus-node`, `vertex-nautilus-health-alert` (+timer), `vertex-ibkr-snapshot-retention` (+timer), `vertex-quant-ibkr-gate-8am` (+timer, disabled; the switch keeps it disabled). |
| `consumers/` | `ibkr-monitor-forced-2fa.sh`, installed as `/opt/ibkr-monitor/forced-2fa.sh`, and `ibkr-monitor-forced-2fa.paused.sh`, which denies 2FA triggers while a switch or rollback runs. `../recovery/vertex_ibkr_recovery.py`, `../recovery/test_vertex_ibkr_recovery.py` and `../status/collect.py` are the other consumers. Each installed consumer must equal its bundle file with only the root path swapped; the switch refuses otherwise. |
| `frozen-manifest.sha256` | SHA-256 of every runtime file carried from `/opt/vertex-quant` (Nautilus node code, portfolio-ui and its build output, `src/`, other scripts), except state, `.env`, installed dependencies and caches. It is the live tree of 2026-10-31 (deploy commit `3511184` plus recorded live edits). Refresh it with `exec_node.py manifest`. |
| `exec_node.py` | `stage`, `gate`, `switch`, `verify`, `rollback`. |

Every file under `runtime/` equals its frozen bytes, with these documented exceptions that `test_exec_node.py` checks:

- `runtime/scripts/nautilus-arm.sh` and `runtime/scripts/nautilus_health_alert.py` differ only in the root path.
- `runtime/nautilus/ibkr_account.py` is the reader from vertex-quant commit `ef1b38b` (merged to its main). The live tree paired the new snapshot script with the old reader, so the snapshot failed with a `TypeError` and the IBKR-only readiness check could never pass. The new reader is a superset of the old one. It is used by the 2FA readiness snapshot and the portfolio-ui snapshot; the running Nautilus image is not rebuilt. It also records each position's `tradingClass`, and `runtime/scripts/ibkr_account_snapshot.py` writes `ibkr-account-classes.json` (conId and tradingClass per position, naming its snapshot and its `captured_at_epoch`; mode 0644 so the gate reads it when root writes it) beside each snapshot. The v1 snapshot shape is unchanged because staged protection checks it key by key. The order policy below needs the sidecar to tell option classes apart; until one that names the newest snapshot and its capture time exists, the gate refuses every option order that may match a held option, and such a snapshot never ends a working option close's reservation.
- `runtime/watchdog/watchdog.py` and `runtime/nautilus/arm_gate.py` carry the kill-switch safety fix (state-machine audit 2026-11-03). While `data/KILL_SWITCH` exists, the gate and the watchdog delete the owner arm record `data/nautilus/ARMED`, so removing the kill switch never re-arms the node; the owner must arm again. `arm_gate.py` also enforces the order policy `options_only_defined_risk_v2` (owner rule 2026-11-04: options only, risk always defined, max loss <= 2% of NLV) in `place_order`. An armed node may only (a) buy an option as a LMT order whose premium (`totalQuantity * lmtPrice * multiplier`; a contract without a multiplier is refused, IBKR's qualified contract names it) is at most 2% of `summary.NetLiquidation.USD` in the newest fresh account snapshot (`NAUTILUS_ORDER_POLICY_MAX_LOSS_PCT` may lower the cap; a value above 2.0 refuses every option buy), or (b) close/reduce a position held in that snapshot while no other close of the same contract is unresolved; every buy of a held-short option is such a close. Orders must name the exact contract (option: expiry, right, strike); an option order only matches a held option when conId or tradingClass is set on both and equal (SPX/SPXW and adjusted classes share symbol, expiry, right and strike), and a held option it can neither match nor tell apart refuses the order. The cap is per order: premium already held or working in the same underlying is not added. The snapshot has no IBKR working orders, so every close the gate places is recorded in `/app/data/nautilus/order-policy-reservations.json` (survives restarts; writers hold an flock on `<file>.lock`). A reservation ends only when (a) a snapshot captured at least 30 s after it shows the position reduced by the order quantity, (b) IBKR reports the order final (Cancelled/ApiCancelled/Filled) to an orderStatus callback the gate observes in this process, and a snapshot captured at least 30 s after that status exists (until then a new close of at most min(held now, the reservation's baseline - filled) may replace it; a modify under the same order id may not exceed its baseline), or (c) the owner releases it with `docker exec <nautilus-trader> python -m nautilus.arm_gate release-close --key <clientId:orderId> --by <actor> --reason <text>` (audited in `arm-audit.jsonl`; list with `... arm_gate reservations`) after checking in TWS that the order no longer works. A cancel request alone ends nothing, and an unreadable file refuses every close. Statuses seen before a restart are lost, and a client that disconnects after placing (for example with a DAY order) sees no later cancel or expiry, so such a close stays reserved until (a) or (c) and blocks node closes of that contract meanwhile. Orders placed outside the gate (TWS, other API clients) stay invisible to it (`test_order_policy.py`). `test_arm_killswitch.py` tests the kill switch. They take effect when the watchdog and Nautilus containers are next rebuilt; the arm_gate change also changes the image version, so the node is DISARMED until the owner arms it again.
- `runtime/nautilus/run_live.py` has no trade-intent source (owner 2026-11-04, card remove-charan-signals). It no longer imports `nautilus/charan.py`, polls the CHARAN Discord signal feed or owns the CHARAN live order transmitter; a legacy `charan` config section and `CHARAN_*` variables are ignored. The node keeps health, IBKR connection state, the arm gate and protection. `test_no_signal_intake.py` checks the file; `test_exec_node.py` pins its digest. It takes effect only after the Nautilus image is rebuilt and the node restarted, which needs an owner-approved time.
- `runtime/docker-compose.yml` sets no `CHARAN_*` variable (owner 2026-11-04, card remove-charan-runtime). They were removed from `nautilus-trader`, `watchdog` and `portfolio-ui`, together with the portfolio-ui login (`PORTFOLIO_AUTH_USERNAME`, `PORTFOLIO_AUTH_PASSWORD`) that `nautilus-trader` received only for the retired intake's 2FA trigger; `portfolio-ui` keeps its login. `portfolio-ui` writes its 2FA rescan request to the same default path as before. `runtime/watchdog/watchdog.py` no longer reads `CHARAN_*` settings or reports them in `live_flags`; a live order path (which makes the IB gateway required) is `TRADING_MODE=live` with `ENABLE_LIVE_TRADING` or `NAUTILUS_RISK_ORDERS_ENABLED`, as before minus the retired transmitter flag (`test_arm_killswitch.py`). `test_exec_node.py` pins the compose digest (`signal_removal`) and the watchdog and arm gate digests (`safety_fix`). The changes take effect when `nautilus-trader`, `watchdog` and `portfolio-ui` are next recreated from this compose file, which needs an owner-approved time.
- `runtime/scripts/transmit_charan_approved_drafts.py` replaces the frozen script (sha256 `a12a52da…`), which called `client.placeOrder` directly and bypassed the arm gate and the order policy. The owned copy refuses every run (exit 2) and never connects to IBKR. portfolio-ui's close button runs it, so that button now reports the refusal; close positions in TWS or IBKR Mobile, or through the armed node (`test_transmit_disabled.py`).
- `python-safety.test.ts` runs these Python tests and the file-only checks of `test_exec_node.py` (`OwnedRuntimeTests`, `ManifestTests`), which pin the digests of the changed files, in CI.

## Invariants

- The compose project name stays `ibkr-nautilus-exec-node` (`name:` in the compose file, `-p` in every command). A new name would create empty named volumes and rename the containers and the network `ibkr-nautilus-exec-node_prototype` that `../history/resolve-gateway.sh` and `../portfolio/resolve-gateway.sh` name. The gate also checks the name each root resolves without `-p`, which the runtime scripts use.
- `gate` compares `docker compose config` of the old and new roots. It passes only when, after replacing the old root path with the new one and dropping retired environment keys, both configs are identical, and when the project, container, network, volume and image names are identical. It also requires that the running `ib-gateway` container's config hash equals the new root's hash. Every compose command of the switch and the rollback names the eight other services only, so compose never stops, recreates or converges `ib-gateway`: no IBKR re-login, no 2FA, and the same bridge IP for vertex-history and vertex-portfolio. The switch refuses to run without a passing gate.
- State is reused: `switch` renames `/opt/vertex-quant/data` (and `portfolio-ui/data`, which holds the portfolio-ui kill switch, when it exists) into `/opt/vertex-exec-node` with `os.rename` after the services that mount it stop. A rename never copies; it fails across filesystems, and the preflight checks that `data/` is not a mount and is on the same filesystem. Nothing is copied or reset.
- The Nautilus node stays DISARMED. The tool reads the arm state (`arm_cli status --json`) and never arms, never sends orders and never prints `.env` values, tokens or compose config values.

## Procedure (root on QuantVPS)

Copy `infra/quant-vps` to the host (for example `/opt/vertex-exec-node-bundle/<commit>/quant-vps`), then:

```sh
python3 exec-node/exec_node.py stage --commit <sha>    # builds /opt/vertex-exec-node; no service changes; rerunnable
python3 exec-node/exec_node.py gate                    # must print "ok": true
python3 exec-node/exec_node.py --dry-run switch        # prints the switch commands
python3 exec-node/exec_node.py switch                  # prints switchDir=/var/lib/vertex-exec-node/switch-<ts>
python3 exec-node/exec_node.py verify --switch-dir <switchDir> --wait 1200
python3 exec-node/exec_node.py rollback --switch-dir <switchDir>   # only when verify fails
```

`switch` first checks the preflight (old root still matches the manifest, new root staged, `.env` unchanged since staging, consumers without drift, no 2FA run in progress, Nautilus DISARMED) and the gate. It then stops `vertex-ibkr-recovery`, installs the paused forced command, stops the health alert timer and the heartbeat, stops and removes the eight non-gateway containers, renames the state, installs the units and consumers (keeping their file modes), runs `docker compose up -d --no-build` for the eight services from the new root, restarts `vertex-nautilus-node`, starts `vertex-ibkr-recovery`, re-creates the pm2 heartbeat from the new root and starts the alert timer again. Backups, the journal and stderr (mode 0600) stay in the switch directory. When a step fails, `switch` runs the rollback at once. `rollback` tolerates a partial switch: stop steps accept absent units and processes, and a state directory that is already back is left in place.

`verify` checks: all nine containers running and healthy, the eight recreated ones from the new root; the gateway container and network unchanged; IBKR account snapshot (the 2FA script with `--check-only`; skipped for the old root, whose reader is broken); vertex-portfolio `state=live`; ibkr-monitor `bridge=live`; Nautilus `armed=false`, no `ARMED` file and an unchanged `arm-audit.jsonl`; no `REMOVED` file in the root; watchdog health; recovery health schema and script path; `vertex-nautilus-node`, the alert timer and recovery active; the 8am gate timer unchanged; the pm2 heartbeat online in the root; no live unit, cron entry, consumer or pm2 entry naming the other root.

Host config (public repository, 2026-11-05): the committed tree names no real host or e-mail. `verify` builds the ibkr-monitor health URL from `VERTEX_TAILNET_IPV4` in the host-local `/etc/vertex/hosts.env` (see `infra/quantvps/README.md`, "Host config"); a missing or malformed value fails the `ibkr_monitor_live` check with the key and file name. The compose file takes the 2FA notice address only from `IBKR_2FA_NOTIFY_EMAIL` in the root `.env` (empty default). The live `/opt/vertex-exec-node` compose still carries its own default, and its `.env` has no `IBKR_2FA_NOTIFY_EMAIL` line (checked 2026-11-05, names only). Add that line to the root `.env` before a root is next built from this tree; `gate` refuses while the two configs differ.

Known gap: `vertex-quant-ibkr-gate-8am.service` runs the script open_ibkr_trading_gate_8am.sh, which does not exist in the live tree. Its timer is disabled, and the switch keeps it disabled.

## Freeze

After a verified switch, vertex-quant gets a FROZEN banner. `/opt/vertex-quant` stays in place, untouched, as the rollback source for 7 days. After 7 stable days it is renamed to `/opt/vertex-quant-frozen-20261031`. Nothing on the host references it after the switch.
